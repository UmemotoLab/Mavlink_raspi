## 2. 安全条件

**この運用は「armed かつ GUIDED」でキーを押すため、機体が実際に動きます。** 次の条件を満たさない限り実施しないでください。

| # | 条件 | 理由 |
|---|---|---|
| 1 | **プロペラを外す**（実飛行させる場合を除く） | 誤キー操作・誤送信でも飛ばない状態にする |
| 2 | **機体を固定する**（拘束具・テザー） | 上昇・水平移動の指令が出ても危険が無いようにする |
| 3 | **周囲から退避する**（半径 2 m 以上を目安、保護メガネ着用） | プロペラ面の延長線上に立たない |
| 4 | **アームは GCS 側で明示的に行う** | AR-hook は arm/disarm を一切送りません（`AR-hook1.py` に arm 送信処理は無い）。アームの主体は常に人間 |
| 5 | **GUIDED への切替も GCS 側で行う** | AR-hook はモード変更を送らない。GUIDED は setpoint が機体に効くモード |
| 6 | **送信機でいつでも GUIDED 解除・ディスアームできる状態** | 本プログラムは機体を止めない（[実験手順書.md](./実験手順書.md) §1） |
| 7 | **`AR-hook1.py` を二重起動しない** | `/dev/ttyAMA0` を占有する。2 本目は接続できず、最悪の場合は破損フレームの原因になる |
| 8 | **中止は Ctrl+C（SIGINT）**。`kill -9` を使わない | SIGKILL 直後に BAD_DATA と偽 armed が観測されている（[BENCH_RESULT.md](./BENCH_RESULT.md) §7.2 / §7.3） |
| 9 | 異音・発熱・焦げ臭・配線外れがあれば即中止 | ベンチでも配線異常は危険 |

> ベンチ計測（[REAL_MACHINE_VERIFY.md](./REAL_MACHINE_VERIFY.md) §1）との違い:
> あちらは「アームしない・GUIDED にしない」条件でリンクだけを測る手順です。
> **本マニュアルはアームと GUIDED を行う**ため、条件 1〜3・6 が必須になります。

## 3. 事前準備

### 3.1 Pixhawk パラメータ

この運用に必要な変更は **2 項目だけ**です（EKF 側プロファイル 157 項目からの差分）。
残り 155 項目と `SERIAL1_BAUD` / `BRD_SER1_RTSCTS` は EKF 側と同じ値を使います
（`setup_AR-hook1.py:10-25`、[統合メモ.md](./統合メモ.md) §10.2）。

| パラメータ | 設定値 | 意味 | 根拠 |
|---|---|---|---|
| `GUID_TIMEOUT` | **30.0** | GUIDED の目標タイムアウト [s]。EKF 側の 3.0 から延長 | `setup_AR-hook1.py:12-16, 148` |
| `GUID_OPTIONS` | **64** | bit 6 = `WPNavUsedForPosControl`（`1 << 6 = 64`）。GUIDED の位置目標を WPNAV 経由にし、`WP_SPD_UP=0.4` / `WP_SPD_DN=0.3` m/s と `WP_ACC_Z=1.5` m/s² を効かせる | `setup_AR-hook1.py:17-23, 149-155` |
| `SERIAL1_PROTOCOL` | 2 | MAVLink2（EKF 側プロファイルの値。AR-hook 用の変更対象ではない） | `setup_AR-hook1.py:247` |
| `SERIAL1_BAUD` | 1000000 | 1,000,000 bps（AR-hook 用の変更対象ではない。EKF 側の値のまま） | `setup_AR-hook1.py:25, 248` |
| `BRD_SER1_RTSCTS` | 2 | ハードウェアフロー制御 有効（AR-hook 用の変更対象ではない。EKF 側の値のまま） | `setup_AR-hook1.py:25, 249` |

**なぜ `GUID_TIMEOUT=30.0` なのか**（`setup_AR-hook1.py:145-148` の設計意図）

- キーボード操作は**キーを押した瞬間に 1 回だけ** setpoint を送ります（押し続けでは送り続けません）。
  既定の 3.0 s では、キーから手を離して 3 秒で GUIDED の目標タイムアウトが成立します。
- スペースキー離陸でも、1.5 m まで上昇している間は AR-hook が setpoint を出しません。
  3.0 s では**上昇中にタイムアウトする**可能性があります。
- そこで 30.0 s に延長し、「キー操作の合間」と「離陸上昇中」をカバーします。

> ファーム側でタイムアウトが成立したときに機体がどう振る舞うか（モード遷移か停止か）は、
> **実機で確認していません（NOT RUN）**。当日はタイムアウトを作らない運用（§6.5）を守ってください。

**なぜ `GUID_OPTIONS=64` なのか**（`setup_AR-hook1.py:149-155`）

- ファーム根拠: `ArduCopter/mode.h` の `Option::WPNavUsedForPosControl = (1U << 6)`、
  `ArduCopter/Parameters.cpp` の `@Bitmask "6:Waypoint navigation used for position targets"`。
- 0 のままでは GUIDED が WPNAV を使わないため、上昇速度・加減速のパラメータが効きません。
- 64 にすると WPNAV 経由になり、上昇 0.4 m/s・下降 0.3 m/s の範囲でゆっくり動きます。
- 戻したいときは `--no-guid-options`（`GUID_OPTIONS` を 0 に戻す）を使います。

### 3.2 パラメータの投入方法

**実装状況: 実装済み**（タスク 28696 / コミット `8abc681` で追加）。
`AR-hook/setup_AR-hook1.py`（1,070 行）が既定で「実機と違う項目だけ」を書き込みます。

```bash
cd AR-hook

# 1) まずは読み取り専用で照合（書き込みなし。終了コード 0=一致 / 1=不一致 / 2=中止）
python3 setup_AR-hook1.py --check

# 2) 差分だけ書き込む（既定動作。AR-hook の差分は GUID_TIMEOUT / GUID_OPTIONS の 2 項目）
python3 setup_AR-hook1.py

# 3) この 2 項目だけを確実に書きたいとき
python3 setup_AR-hook1.py --only GUID_TIMEOUT,GUID_OPTIONS

# 4) 接続せずに QGC 用 .param を書き出す（既定の出力先: AR-hook/params/arhook1.param）
python3 setup_AR-hook1.py --export-param
```

- 既定の接続先は `--device auto`（`/dev/ttyACM0` → `/dev/ttyAMA0`）。UART の baud は設定辞書の
  `SERIAL1_BAUD` を単一の出典として使います（`setup_AR-hook1.py:624-625`）。
- `/dev/ttyAMA0` を掴んでいる `mavlink-bridge.service` は**実行中だけ自動停止し、終了時に再起動**します
  （`setup_AR-hook1.py:43-44, 574-576`）。止めたくない場合は `--no-stop-bridge`。
- 書き込み前に HEARTBEAT の armed を確認し、**armed なら中止**します（`--force` でのみ続行。非推奨）。
- 終了コード: **0=成功 / 1=不一致 / 2=中止**（armed・接続失敗・引数エラー）。
- AR-hook ディレクトリには uv プロジェクトが無いため、uv で固定したい場合:
  `cd AR-hook && uv run --project ../EKF --frozen python setup_AR-hook1.py --check`

**手動で投入する場合（スクリプトを使わないとき / 照合の裏取り）**

GCS の Full Parameter List で次の 2 項目を設定し、**Write / Save してから読み戻して確認**します。

```text
GUID_TIMEOUT = 30.0
GUID_OPTIONS = 64
```

`param set` を使えるコンソール（MAVProxy 等）では次のとおりです。

```text
param set GUID_TIMEOUT 30.0
param set GUID_OPTIONS 64
param fetch GUID_TIMEOUT
param fetch GUID_OPTIONS
```

- `setup_AR-hook1.py` は PARAM_SET 後に FC が自動保存する前提で、明示保存コマンドを送りません
  （`setup_AR-hook1.py:46-47`）。手動で設定した場合も同じ扱いで構いませんが、
  電源再投入後に `--check` で残っていることを確認してください。
- **注意**: `setup_AR-hook1.py` の書き込みは SITL で「差分のみ書き込み → 読み戻し一致」まで確認済みですが、
  **実機 FC への書き込みは未実施（NOT RUN）**です（[統合メモ.md](./統合メモ.md) §10.2）。

### 3.3 接続とポート占有の確認

```bash
cd AR-hook

# 1) 二重起動・残骸プロセスの確認（期待: すべて 0 行。pgrep の終了コード 1 は「該当なし」で正常）
#    ブラケット記法 [b]ench_check は自己マッチ防止（bash -c の自分自身のコマンドラインを拾わない）
pgrep -af "[b]ench_check\.py|[A]R-hook1\.py|[s]end_GPS3\.py"
pgrep -af "[m]avlink"
```

- **ブラケット記法を崩さないでください。** `bash -c` 経由で実行すると、シェル自身の
  コマンドライン（例: `/bin/bash -c ...`）にパターン文字列そのものが含まれる場合があり、
  そのとき `pgrep -af` は**自分自身にマッチ**します（実機で PID 1490 = `/bin/bash -c ...` を検出。
  [REAL_MACHINE_VERIFY.md](./REAL_MACHINE_VERIFY.md) §3.1）。`[A]R-hook1\.py` は
  コマンドライン上の文字列 `[A]R-hook1\.py` と一致しないため自己マッチしません。
- **このゲートは単独で実行してください。** 同じ `bash -c` に `systemctl ... mavlink-bridge` や
  `AR-hook1.py` の起動行を含めると、その文字列で自己マッチします（下の 3)・4) は別ブロックです）。
- 1 行でも出た場合は、対象 PID を特定 → `kill <PID>`（SIGTERM）→
  `sudo fuser -v /dev/ttyAMA0` が空（0 件）を確認 → 起動、の順で進めます。

```bash
# 2) ポートを掴んでいるプロセス（要 root。0 件＝出力なしが正常）
sudo fuser -v /dev/ttyAMA0
sudo lsof /dev/ttyAMA0
```

- **`send_GPS3.py` がポートを掴んでいる場合は必ず停止してください。** 15 Hz の GPS_INPUT が
  Pixhawk に混入し、EKF の状態が変わって**計測条件が汚染**されます
  （[REAL_MACHINE_VERIFY.md](./REAL_MACHINE_VERIFY.md) §3.1）。
- `AR-hook1.py` が 1 行でも出たら **Ctrl+C（SIGINT）または `kill <PID>`（SIGTERM）** で
  正常終了させます。`kill -9` は使わないでください
  （[REAL_MACHINE_VERIFY.md](./REAL_MACHINE_VERIFY.md) §3.1）。

```bash
# 3) mavlink-bridge が動いていたら停止する（AR-hook1.py は自動停止しない）
systemctl is-active mavlink-bridge
sudo systemctl stop mavlink-bridge
```

```bash
# 4) UART の状態（Bluetooth に取られていない / getty が無い）
ls -l /dev/serial0 /dev/ttyAMA0
cat /proc/cmdline            # console=serial0,... が残っていないこと
dmesg | grep -i tty          # overrun / frame error が無いこと
```

- `mavlink-bridge` は `setup_AR-hook1.py` が一時停止→再起動しますが、**`AR-hook1.py` 自身は停止しません**。
  手動で止めてから起動してください（起動後に再起動しないこと）。
- 停止したまま忘れると他ツールが繋がりません。実験終了後に
  `sudo systemctl start mavlink-bridge` で戻すか、戻さない運用を決めておいてください。

- 本マニュアル作成時点の `AR-hook1.py` には、**周期再送の専用実装はありません**。
  現在の setpoint 送信は次の 2 経路だけです。
  1. **キーボード**: キーを押した瞬間に 1 回（`control_loop()` → `send_local_target()`、`AR-hook1.py:3493-3505`）。
  2. **カメラ追従**: 毎フレーム（40 Hz、`AR_MEASUREMENT_FPS = 40`、`AR-hook1.py:106-108`）。
- したがって「カメラが動いていない状態でキーだけ」のときは setpoint が断続的になります。
  これが `GUID_TIMEOUT=30.0` を必要とする理由です（§3.1 / §6.5）。
- 環境変数を設定しても**エラーにならず、単に無視されます**（読むコードが無いため）。

**関連する環境変数（本書の対象外）**: `AR_HOOK_GPS_INPUT_ENABLE`（既定 `0`）、
`AR_HOOK_START_LAT` / `AR_HOOK_START_LON` / `AR_HOOK_START_HEIGHT_M`、
`AR_HOOK_AUTO_START_*`、接続系の `AR_HOOK_CONNECTION` / `AR_HOOK_SITL` / `AR_HOOK_DEVICE` /
`AR_HOOK_BAUD` / `AR_HOOK_RTSCTS`。一覧は [実験手順書.md](./実験手順書.md) §1.1 を参照してください。

**推奨の起動（本運用）** — 何も付けないのが既定です。

```bash
cd AR-hook
python3 AR-hook1.py
```

南向き（180°）固定で実験する場合だけ、次を使います。


## 5. キー操作表

`control_loop()` は **50 ms 周期**で 1 文字ずつ読みます（Enter 不要・`AR-hook1.py:3434-3513`）。
キーは **NED ローカル座標**（`x`=北, `y`=東, `z`=Down）を直接動かします。1 回の移動量は `STEP = 0.10` m です。

| キー | 動作 | 内部の変化 | 有効条件 | 実装 |
|---|---|---|---|---|
| `SPACE` | **離陸**（1 回だけ） | `MAV_CMD_NAV_TAKEOFF`（高度 `TAKEOFF_ALT` = 1.50 m） | **確定 GUIDED かつ確定 armed** | `AR-hook1.py:1326-1366, 3441-3444` |
| `u` | 南（`-N`） | `x -= 0.10` | GUIDED であれば離陸前でも送信され得る | `AR-hook1.py:3454` |
| `m` | 北（`+N`） | `x += 0.10` | 同上 | `AR-hook1.py:3455` |
| `h` | 東（`+E`） | `y += 0.10` | 同上 | `AR-hook1.py:3456` |
| `l` | 西（`-W`） | `y -= 0.10` | 同上 | `AR-hook1.py:3457` |
| `w` | 上 | `z -= 0.10`（Down を減らす） | **離陸高度到達後**（`initial_target_set`）のみ | `AR-hook1.py:3458` |
| `z` | 下 | `z += 0.10` | 到達後のみ。離陸地点から **0.05 m** を下回る操作は無効 | `AR-hook1.py:3459-3468` |
| `t` | 基準点復帰 | N/E を開始位置、高さを離陸地点から **1.50 m** に設定 | 到達後のみ | `AR-hook1.py:3469-3479` |
| `q` | 終了 | `running = False`（ループを抜ける） | 常時。機体へは何も送らない | `AR-hook1.py:3436` |

- `w` / `z` / `t` は「離陸高度到達（`initial_target_set = True`）」まで**押しても何も起きません**（表示も出ません）。
- `t` の開始位置の既定値は `EXPERIMENT_START_LAT/LON = 36.0757693 / 136.2132945`、
  高さ `EXPERIMENT_START_HEIGHT_ABOVE_TAKEOFF = 1.50` m です（`AR-hook1.py:369-371, 400-401`、
  `AR_HOOK_START_LAT` / `AR_HOOK_START_LON` / `AR_HOOK_START_HEIGHT_M` で変更可）。
- キー操作は必ず `commit_target_command()` を通るため、§6.3 のクランプが掛かります
  （クランプは「現在位置から目標まで」の偏差。上限に達した状態で押すと、表示の数値が伸びません）。

### 5.1 機首を 180°（南）に固定している場合の「前後」

キーは**機体の前後ではなく NED（北・東）**を動かします。機首は `AR_HOOK_TARGET_YAW_DEG` で固定です。
`AR-hook1.py:3429-3431` の画面表示どおり、**機首 180°（南）では `m`（北）が「後退」**になります。

| 機首 | 前進になるキー | 後退になるキー | 右 | 左 |
|---|---|---|---|---|
| `0°`（北・既定） | `m`（北） | `u`（南） | `h`（東） | `l`（西） |
| `180°`（南） | `u`（南） | `m`（北） | `l`（西） | `h`（東） |
| `90°`（東） | `h`（東） | `l`（西） | `u`（南） | `m`（北） |

> **注意**: 機首 180° のとき「`u` が後退」ではありません。実装（`AR-hook1.py:3454-3455` のキー処理と
> 3429-3431 の画面表示）に合わせると **`u`＝前進 / `m`＝後退**です。押す前に画面の 1 行を必ず読み直してください。

## 6. 挙動の説明

### 6.1 離陸高度と到達判定

| 項目 | 値 | 実装 |
|---|---|---|
| 離陸目標高度 | `TAKEOFF_ALT = 1.50` m（**床＝EKF home 相対**） | `AR-hook1.py:98`（`AR_HOOK_TAKEOFF_ALT_M` で上書き可） |
| 離陸指令 | `MAV_CMD_NAV_TAKEOFF`（`comm.takeoff(alt)`）を 1 回だけ | `AR-hook1.py:1321-1323, 1358-1364` |
| 再送しない仕組み | `space_takeoff_sent` フラグ（押し続け・キーリピートでも 1 回だけ） | `AR-hook1.py:1347-1351` |
| 到達判定 | `GLOBAL_POSITION_INT.relative_alt >= TAKEOFF_ALT × 0.9`（= **1.35 m**） | `AR-hook1.py:1981-1983` |
| 到達時の処理 | `initial_target_set = True`、`target['z']` を「home + 1.50 m」に初期化 | `AR-hook1.py:1987-1991` |

- 0.9 倍にしているのは「目標高度に届く直前で追従を開始できるようにする」ためです
  （SITL 実測では 1.359 m で到達判定：§12.3 の `timeline`）。
- `space_takeoff_sent` は**セッション中 1 回だけ**です。GUIDED を解除して入り直しても再送しません
  （`AR-hook1.py:1337-1338`）。もう一度離陸させたいときはプログラムを再起動してください。

### 6.2 到達後の初期 target（重要）

- 到達時に初期化されるのは **`target['z']` だけ**です（`AR-hook1.py:1987-1989`）。
  `target['x']` / `target['y']` は起動時の初期値 **`0.0, 0.0`（= REF 原点）** のままです（`AR-hook1.py:465`）。
- **マーカーが検出できている場合**、到達後の最初のフレームで「現在位置 + 相対ベクトル」に上書きされ、
  実際の目標は機体位置基準に移ります（`AR-hook1.py:2579` 以降）。
- **カメラ追従が動いていない（ArUco 初期化失敗・カメラ無し）場合**は、目標が REF 原点のまま残ります。
  この状態でキーを押すと、REF 原点を基準に ±0.10 m 動かす指令になります。当日は必ず `ArUco:` 行を確認してください。
- 手動で開始位置へ寄せる一番確実な方法は `t`（基準点復帰）です。開始位置そのものへ目標を置き直します。

### 6.3 クランプ（目標の上限）

すべて `commit_target_command()` に集約されています（`AR-hook1.py:2064-2138`、実体は [`target_limiter.py`](./target_limiter.py)）。

| 制限 | 値 | 意味 | 定数 |
|---|---|---|---|
| 目標移動速度 | **0.50 m/s** | 1 フレーム 0.0125 m（40 Hz 換算）。**カメラ追従のみ**適用 | `TARGET_MAX_SPEED_MPS` / `TARGET_MAX_STEP_M`（`AR-hook1.py:114-117`） |
| 水平偏差 | **1.20 m** | **現在位置からの半径**。超えると方位を保ったまま距離を縮める | `TARGET_MAX_OFFSET_M`（`AR-hook1.py:118`） |
| 上昇側偏差 | **0.30 m** | 現在位置から上へ 0.30 m まで | `TARGET_MAX_ALT_UP_M`（`AR-hook1.py:119`） |
| 下降側偏差 | **0.20 m** | 現在位置から下へ 0.20 m まで | `TARGET_MAX_ALT_DOWN_M`（`AR-hook1.py:120`） |

- キーボードは `apply_rate_limit=False` で呼ばれるため（`AR-hook1.py:3485`）、**レートリミッタは掛かりません**。
  1 回の `STEP`（0.10 m）がそのまま反映されます。
- ただし**偏差クランプはキーボードにも掛かります**。現在位置から見て上限を超える操作は頭打ちになり、
  押し続けても目標だけが先行することはありません（機体が追従して現在位置が近づけば再び動く、という
  挙動を想定していますが、**実機での確認は NOT RUN**）。
- 実機で「押しても数値が伸びない」ときは、クランプ（水平 1.20 m / 上 0.30 m / 下 0.20 m）を疑ってください。

### 6.4 setpoint の送信タイミング（再送）

| 経路 | 送信タイミング | 実装 |
|---|---|---|
| キーボード | キーを押した瞬間に **1 回だけ**（押し続けでは送らない） | `AR-hook1.py:3434-3505` |
| カメラ追従 | 毎フレーム（**40 Hz**、`AR_MEASUREMENT_FPS = 40`） | `AR-hook1.py:106-108` |
| 周期的再送（`AR_HOOK_SETPOINT_RESEND_HZ`） | **未実装**（タスク 90703 で実装予定） | 該当コードなし |

- カメラ追従経路は、**一度でも検出で目標を更新した後**に限り、検出ロスト時も保持／減衰の目標を送ります
  （`update_target_on_detection_lost()`、`AR-hook1.py:2141-2193`）。一度も検出していない間
  （`_target_tracked_once = False`）は目標を変更せず、送信もしません。
- 送信は必ず `can_send_guided_setpoint()` を通ります（GUIDED 以外・home 未確定では送らない）。
  キーボード経路は「離陸到達」を条件にしません（離陸前の `u/m/h/l` を許可するため `target_ready=None`）。
- 座標変換は `send_local_target()` の 1 箇所だけです（REF 基準 NED → home 相対高度、`AR-hook1.py:1386-1409`）。

### 6.5 GUIDED タイムアウト（`GUID_TIMEOUT` = 30 s）との関係

- ファームは「GUIDED で目標を最後に受けてから `GUID_TIMEOUT` 秒」でタイムアウトを判定します。
  AR-hook 側は既定 30.0 s を前提に動きますが、**タイムアウトを検出するコードは持っていません**
  （`AR-hook1.py` に `GUID_TIMEOUT` の記述は無い）。
- **タイムアウトを作らないための実務ルール**
  1. 離陸上昇中（スペース後〜`✓ 離陸高度到達`）は**他の操作をしない**。
  2. 離陸後、**30 秒以上キーから手を離さない**。手を離す時間が長くなるときは `t` を 1 回押す、
     またはカメラ追従を動かしておく（追従中は 40 Hz で送信され続ける）。
  3. どうしても間が空くときは、GCS 側で GUIDED から外す（＝タイムアウトを待たずに自分でモードを決める）。
- タイムアウトが成立したときの機体の挙動（モード遷移かホバー保持か）は
  **実機で確認していません（NOT RUN）**。§8 の「勝手に降下／停止する」を参照してください。

### 7.4 `HB遷移:` と `HB生値:`

（SITL 実出力。同じ `run.log` から）

```text
HB遷移: armed False->True mode UNKNOWN(None)->GUIDED(4) sys=1 comp=1 base_mode=0xD9 custom_mode=4 armed_raw=True guided_raw=True heartbeat_age_s=1.000 confirm=2
```

```text
HB生値: armed=True armed_raw True->False mode GUIDED(4)->GUIDED(4) confirm_mode=GUIDED(4) sys=1 comp=1 base_mode=0x59 custom_mode=4 guided_raw=True heartbeat_age_s=1.000 confirm=2
HB遷移: armed True->False mode GUIDED(4)->GUIDED(4) sys=1 comp=1 base_mode=0x59 custom_mode=4 armed_raw=False guided_raw=True heartbeat_age_s=1.000 confirm=2
```

| 行 | いつ出るか | 読み方 |
|---|---|---|
| `HB遷移:` | **確定値**（armed / モード）が変化した | `armed False->True` は実際にアームされた（**本運用では意図した動作**）。`armed True->False` はディスアーム＝プログラム終了 |
| `HB生値:` | 確定値は変わらないが**生値**が動いた（偽 armed の切り分け用） | `armed_raw True->False` のような 1 回だけの変化は「破損フレームを 1 件見た」程度。**繰り返し出るなら偽 armed を疑う** |

- `base_mode` は 16 進。`0x80` ビットが SAFETY_ARMED、`0xD9` は armed + 各種モードフラグ、
  `0x59` はディスアーム相当です。
- `heartbeat_age_s` は「直前の採用フレームからの経過秒」。1.0 秒前後なら正常、
  極端に小さい値は重複・バースト、大きい値は受信欠落の手がかりです
  （[FAILSAFE_CHECKLIST.md](./FAILSAFE_CHECKLIST.md) §1.3.1）。
- `confirm=2` は「2 連続フレームで確定」の設定値（`ARHOOK_HB_CONFIRM_FRAMES`）。
- これらは `bench_log_check.py` が合否判定に使います（CSV には含まれないため、テキストログを保存してください）。

## 8. 異常時の対応表

判定に迷ったら**まず送信機で GUIDED を解除**してください。AR-hook は機体を止めません。

| 症状 | 原因候補 | 対処 |
|---|---|---|
| **キーを押しても動かない**（`KEY:` 行すら出ない） | ① キーボード制御が無効（`⚠ キーボード制御を無効化します`）。stdin が端末でない | 対話端末で起動し直す。疑似 TTY が必要なら `script -q /dev/null python3 AR-hook1.py`（[SITL_SETUP.md](./SITL_SETUP.md) §10） |
| 〃 | ② 映像ウィンドウ側にフォーカスがある | 端末ウィンドウをクリックしてから押す |
| 〃 | ③ 押したキーが `w/z/t` で、まだ離陸高度到達前 | `✓ 離陸高度到達` を待つ（`AR-hook1.py:3458-3479`） |
| **`KEY:` は出るが機体が動かない** | ① GUIDED でない（`⚠ Guidedモードではないため目標を送信しません`） | GCS で GUIDED に切替（`AR-hook1.py:3506-3507`） |
| 〃 | ② home 相対高度が未確定（`⚠ 離陸地点の高度が未確定...`） | `GLOBAL_POSITION_INT` の受信を確認。EKF の home 設定を GCS で確認（`AR-hook1.py:3508-3509`） |
| 〃 | ③ クランプ上限に達している（数値が伸びない） | §6.3。現在位置から水平 1.20 m / 上 0.30 m / 下 0.20 m が上限 |
| **スペースで離陸しない** | ① `⚠ スペース離陸: GUIDED モードではないため送信しません` | GCS で GUIDED を確認（確定値で判定。2 連続フレーム必要） |
| 〃 | ② `⚠ スペース離陸: 未 armed のため送信しません` | GCS で arm。`HB遷移: armed False->True` を確認してから押す |
| 〃 | ③ `ℹ スペース離陸: 送信済みです（...再送しません）` | 仕様（1 セッション 1 回）。再離陸はプログラム再起動 |
| 〃 | ④ そもそも反応が無い（`KEY:` も出ない） | キーボード制御の無効（上記） |
| **上昇しない／上昇が遅い** | ① `GUID_OPTIONS` が 0（WPNAV を使わない） | `setup_AR-hook1.py --check` で 64 を確認（`--no-guid-options` で 0 に戻していないか） |
| 〃 | ② `GUID_TIMEOUT=3.0` のまま（離陸上昇中にタイムアウト） | `--check` で 30.0 を確認し、必要なら `--only GUID_TIMEOUT` で投入 |
| 〃 | ③ NAV_TAKEOFF 自体が拒否された（EKF/GPS 未準備） | GCS の Messages を確認。armed と EKF の状態を確認。**拒否されても `space_takeoff_sent` は立つ**ので、直すときはプログラム再起動 |
| **勝手に降下／停止する** | GUIDED の目標が `GUID_TIMEOUT`（30 s）途切れた、または GUIDED から外れた | 送信機でモードを確認し、必要なら手動で LOITER / LAND。**タイムアウト時の機体挙動は実機 NOT RUN**（§6.5） |
| 〃 | カメラ追従が止まり、キーも押していない | `t` を押して目標を送り直す。`ATTITUDE` の stale 警告が出ていないか確認 |
| **偽 armed 警告が出る**（`HB生値:` に `armed_raw=True`） | 破損フレーム・多重起動・`kill -9` の直後 | 1 件は記録して続行。**2 件以上（繰り返し）は中止**。`sys` / `comp` / `base_mode` を保存し [REAL_MACHINE_VERIFY.md](./REAL_MACHINE_VERIFY.md) §6.1 に従う |
| **リンク断**（`❌ MAVLinkリンク切断を検出 → プログラムを終了します`） | ケーブル・コネクタ・RTS/CTS・電源 | プログラムは終了し CSV を保存する（`AR-hook1.py:1882-1886`）。機体は送信機で回収。配線と `/dev/ttyAMA0` の占有を確認 |
| **ディスアームしたら終了した**（`✓ ディスアーム検出`） | 仕様（`AR-hook1.py:1928-1931`） | 記録は保存済み。続けるなら再起動（再 arm・再 GUIDED・スペースからやり直し） |
| **ArUco が出ない**（`❌ ArUco ディテクタを初期化できません`） | OpenCV の版・`cv2.aruco` の有無 | 追従ループは開始されない。キー操作と離陸は動くが、実験（追従）は成立しない。OpenCV の版を確認 |

- 中止の合図は **`q` → 送信機で GUIDED 解除 → 着陸 → ディスアーム**です（§9）。
- 迷ったときの原則: **AR-hook を止めるより先に、機体を安全なモードにする**。

## 9. 終了手順

順序を守ってください（CSV は終了処理の最後に保存されます）。

1. **キーボードで `q`**（`AR-hook1.py:3436`）。状態を確認したいだけなら押さない。
2. 画面に次の順で出るのを待つ（`finalize_shutdown()`、`AR-hook1.py:3830-3884`）。

```text
記録終了、CSV保存中...
✓ CSV保存完了: /home/<user>/LOGS_Pixhawk6c/<日時>_1.csv (<行数> 行)
✓ プログラム終了
```

3. **CSV の存在とサイズを確認**（保存先は `CSV_DIR = Path.home() / "LOGS_Pixhawk6c"`、`AR-hook1.py:441-442`）。

```bash
ls -l ~/LOGS_Pixhawk6c/ | tail -5
head -1 ~/LOGS_Pixhawk6c/<日時>_1.csv | cut -c1-120   # ヘッダ行が読めること
```

4. **送信機／GCS でディスアーム**（すでにディスアームで終了した場合は不要）。
5. **電源断**。Raspberry Pi のシャットダウン → Pixhawk の電源断の順で行います。

```bash
sudo shutdown -h now
```

- `q` を押しても終了しない場合は **Ctrl+C（SIGINT）**。`kill -9` は使わないでください。
- 映像出力で `1: 本体画面` を選んでいる場合、ウィンドウの `q`（`cv2.waitKey`）でも終了できます。
- `✓ CSV保存完了` が出ないまま端末が戻った場合は、`~/LOGS_Pixhawk6c/` を確認し、
  無ければ [実験手順書.md](./実験手順書.md) §7.3「記録が残らないケース」を参照してください。

  （`verify_sitl.py:88-92, 1707-1913`）。
- 実 SITL では setpoint を 10 Hz で再送して GUIDED タイムアウトを避けます（本番は 40 Hz）。

### 11.4 SITL で練習しても実機の代わりにならない項目

| 項目 | 理由 |
|---|---|
| シリアル（`/dev/ttyAMA0` 1,000,000 bps / RTS-CTS） | SITL は UDP。配線・フロー制御・ボーレートは再現されない |
| RTS/CTS・ケーブル起因のリンク断 | 同上 |
| 実機の上昇速度・風・地面効果 | SITL のダイナミクスは実機と異なる |
| Motive（`Motive_*` 列） | SITL では N/A。屋内の位置推定は再現されない |
| GUIDED タイムアウトの実挙動 | `verify_sitl.py` 側が 10 Hz で再送するため、タイムアウトを作らない |
