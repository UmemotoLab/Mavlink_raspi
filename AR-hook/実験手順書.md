## 0. 最初に読む：この実装の危険な性質

### 0.1 離陸は「スペースキー」で行う（自動離陸は既定で無効）

本運用の流れは次のとおりです。

```
GCS で GUIDED → arm → （パソコンのキーボードで）スペースキー
        ↓  「✓ スペースキーで離陸指令（1.5m）」
   MAV_CMD_NAV_TAKEOFF（param7 = 1.5 m）を 1 回だけ送信
        ↓  relative_alt >= 1.35 m（1.5 m × 0.9）
   追従目標の送信を許可 → 以後はキーボードで前後左右上下を手動調整
```

- スペースキーの離陸指令は**1 回だけ**です。押し続け・キーリピートでも再送しません（送信済みフラグ `space_takeoff_sent`）。
- 前提条件は `monitor_vehicle()` が `HEARTBEAT` から確定した **GUIDED** と **armed**（通信部の 2 連続フレーム確定値）です。
  満たさない場合は送らず、`⚠ スペース離陸: GUIDED モードではないため送信しません` /
  `⚠ スペース離陸: 未 armed のため送信しません（先に arm してください）` を **1 行だけ**表示します。
- 離陸目標高度は `TAKEOFF_ALT = 1.50` m（床＝EKF home からの高さ）です。環境変数 `AR_HOOK_TAKEOFF_ALT_M`（0.3〜5.0）で変更できます。
- **GUIDED＋アームから 3 秒後に自動で離陸する従来動作は既定で無効**です（`AR_HOOK_AUTO_TAKEOFF=0`）。
  必要なときだけ `AR_HOOK_AUTO_TAKEOFF=1` を指定すると従来どおり動きます（SITL 検証・旧手順の再現用）。
- 自動離陸を有効にした場合の注意（`AR_HOOK_AUTO_TAKEOFF=1` のときだけ該当）:
  - この判定は**オペレータの確認を挟みません**。ボタンもキー入力も不要です。
  - 判定の契機は `HEARTBEAT`（通常 1 Hz）なので、実際の送信は「3 秒経過後の次の HEARTBEAT」＝およそ **3〜4 秒後**です。
  - GUIDED を解除すると `takeoff_sent` などがリセットされるため、**アームしたまま GUIDED へ入り直すと再び 3 秒後に離陸指令が出ます**。
  - プロンプト待ちの間も `monitor_vehicle()` は動いています（対話 2 の直後に開始）。したがって「起動スクリプトを走らせている最中に GUIDED＋アーム」しても自動離陸します。
- スペース離陸は 1 セッション 1 回だけです。GUIDED を解除して入り直しても、スペースキーでは再送しません（必要ならプログラムを再起動してください）。

### 0.2 その他の注意

| 注意 | 内容 |
|---|---|
| 離陸前のキー操作 | `u` / `m` / `h` / `l` は**離陸前でも** setpoint を送ります。送信条件は「**GUIDED 中**」かつ「離陸地点の Down が確定していること」だけです（高度到達は不要）。起動直後に GUIDED のまま誤ってキーを叩くと目標が動きます。GUIDED 以外では `⚠ Guidedモードではないため目標を送信しません` と表示され送信しません。 |
| 終了は停止ではない | `q` キー・Ctrl+C は**プログラムを終了するだけ**で、ディスアームも着陸も送りません。機体を止めるのは送信機側の操作です。 |
| 映像記録 | MP4 が作られるのは映像出力で `1: 本体画面` を選んだときだけです（`2` / `3` では MP4 は作られません）。 |
| 記録の保存 | CSV は**終了処理時に 1 回だけ**書き出します。プロセスを `kill -9` などで強制終了すると記録は失われます。 |

## 1. システム構成と前提

| 要素 | 前提 |
|---|---|
| 機体 | Pixhawk 6C / ArduPilot（ArduCopter）。GUIDED の `custom_mode == 4` |
| コンパニオン | Raspberry Pi 5。カメラは Picamera2（1640×1232）または USB カメラ |
| 接続 | **実機はシリアル 1 本（TELEM1 `/dev/ttyAMA0` 1,000,000 bps RTS/CTS）のみ**。USB は使わない。1 本で GPS_INPUT 供給と ArUco 誘導を両立するため、AR-hook 自身が送る `AR_HOOK_GPS_INPUT_ENABLE=1`（§3.1.1）を使う |
| モーションキャプチャ | Motive → UDP **15770**（`Motive_RB1`＝機体, `RB2`＝荷物, `RB3`＝カメラ）。現行 `main()` が起動するのは 15770 の受信スレッドのみ（15769 の `motive_udp_listener` は未起動。[ARCHITECTURE.md](./ARCHITECTURE.md) 参照） |
| 座標原点 | [local_frame.py](./local_frame.py) の `REF_LAT/REF_LON/REF_ALT` 固定。起動時原点への正規化は行わない |
| 送信機 | **いつでも GUIDED 解除・ディスアームできる状態**で実験すること（本プログラムは機体を止めない） |

### 1.1 起動時に効く環境変数

| 変数 | 既定 | 範囲 | 効果 |
|---|---|---|---|
| `AR_HOOK_TARGET_YAW_DEG` | `0.0` | `0.0`〜`360.0` [deg] | 目標 yaw（MAVLink NED、0=北、90=東、180=南）。実行時に固定値で送信 |
| `AR_HOOK_MASK` | `0x09F8` | `0x0000`〜`0xFFFF` | `SET_POSITION_TARGET_GLOBAL_INT` の type_mask。yaw を無効化する例: `0x0DF8` |
| `ARHOOK_ATTITUDE_STALE_TIMEOUT_MS` | `100` | 正の有限値 [ms] | ATTITUDE 鮮度しきい値。超過で自動追従を停止 |
| `AR_HOOK_TAKEOFF_ALT_M` | `1.50` | `0.30`〜`5.00` [m] | 離陸目標高度（床＝EKF home 相対）。スペースキー離陸・自動離陸の両方に効く |
| `AR_HOOK_AUTO_TAKEOFF` | `0`（無効） | `0` / `1` | `1` で GUIDED+armed 3 秒後の自動離陸（従来動作）を復活。**本運用では使わない** |
| `AR_HOOK_GPS_INPUT_ENABLE` | `0`（無効） | `0` / `1` | `1` で AR-hook 自身が Motive 剛体 ID=1 の位置から GPS_INPUT を **15Hz** で送る（REF 基準・AMSL）。有効時は **`send_GPS3.py` を同時に動かさない**（§3.1.1） |
| `AR_HOOK_AUTO_START` | `0`（無効） | `0` / `1` | `1` で離陸後に開始位置へ自動移動してからカメラ追従（TRACK）を開始。**本運用では使わない**（§4.2.1） |
| `AR_HOOK_SETPOINT_RESEND_HZ` | `5` | `0`〜`20` [Hz] | キー入力・カメラ検出が無い間も target を再送する周期（0 で無効）。5Hz = 0.2 秒周期（§4.3） |
| `AR_HOOK_START_LAT` / `AR_HOOK_START_LON` | `36.0757693` / `136.2132945` | 緯度 ±90 / 経度 ±180 [deg] | 実験開始位置（キーボード `t` と共通） |
| `AR_HOOK_START_HEIGHT_M` | `1.50` | `0.05`〜`10.0` [m] | 開始位置の高さ（離陸地点から）。既定値を `1.10` から `1.50` へ変更（離陸高度と整合） |
| `AR_HOOK_AUTO_START_ARRIVE_XY_M` / `_Z_M` | `0.15` / `0.10` | `0.01`〜`5.0` [m] | 到着判定の水平距離 / 高さ差 |
| `AR_HOOK_AUTO_START_ARRIVE_FRAMES` | `2` | `1`〜`1000` | 到着判定を連続で満たすフレーム数 |
| `AR_HOOK_AUTO_START_TIMEOUT_S` | `30.0` | `0.1`〜`600.0` [s] | 自動移動のタイムアウト（超過時は現在目標を保持） |

- 値が数値でない・範囲外の場合は、**起動時にメッセージを出して停止**します（実験中には変わりません）。
- 実際に送る yaw は `TARGET_YAW_SEND_DEG = AR_HOOK_TARGET_YAW_DEG + CAMERA_MOUNT_YAW_OFFSET_DEG`（取付ヨーオフセットの既定は `0.0`）です。起動ログの 1 行目に実送信値と設定ソースが出ます。

## 3. 起動手順

### 3.1 実行コマンド

```bash
cd AR-hook
# 例: 南向き固定（180°）で実験する場合
AR_HOOK_TARGET_YAW_DEG=180.0 python3 AR-hook1.py
```

- 何も指定しなければ yaw は `0.0`（北向き）、`MASK` は `0x09F8` です。
- Python 依存（`pymavlink` / `opencv` / `numpy` / `picamera2` / `pytz`）は [requirements.txt](./requirements.txt) を参照してください。
- 同じ `/dev/ttyAMA0` を他プロセス（例: `mavlink-bridge.service`）が開いていると接続できません。
  `EKF/MEMORY_BANK.md` の運用手順に従い、必要ならサービスを停止してから起動します。

#### 3.1.1 1 ポート運用（AR-hook が GPS_INPUT も送る）

実機はシリアル 1 本しか使えないため、`send_GPS3.py`（15Hz で GPS_INPUT を送る独立プロセス）と AR-hook を同時に動かすと **同じ `/dev/ttyAMA0` を奪い合います**。次のどちらか一方だけを使ってください。

| 運用 | 起動方法 | 備考 |
|---|---|---|
| **推奨: AR-hook が GPS_INPUT も送る** | `AR_HOOK_GPS_INPUT_ENABLE=1 python3 AR-hook1.py` | 1 プロセスがポートを所有。Motive 剛体 ID=1 の位置から 15Hz（REF 基準・AMSL）で送る。ArUco 誘導と同時に動く |
| 従来: `send_GPS3.py` + AR-hook | `send_GPS3.py` を起動し、AR-hook 側は `AR_HOOK_GPS_INPUT_ENABLE=0`（既定） | 2 プロセスが同じポートを開くため**実機では成立しない**（USB 等の別ポートが必要。§3.1.2） |

- 有効時の起動ログ（`AR_HOOK_GPS_INPUT_ENABLE=1`）:
  ```
  GPS_INPUT: 有効（15Hz, REF基準）
  ⚠ GPS_INPUT: send_GPS3.py を同時に動かさないでください（同じ Pixhawk への二重送信は EKF を混乱させます）
  ```
- **二重送信禁止**: AR-hook の GPS_INPUT が有効なときに `send_GPS3.py` を起動しないでください。EKF が 2 系統の位置入力で混乱します（コードでのプロセス検知はしません）。
- 送信は Motive の剛体 ID=1 を受信してから始まります（未受信の間は送りません）。Motive が途絶えると最後の 1 件を送り続けるため、飛行中は Motive UDP 15770 の受信を監視してください。
- 終了時は「GPS 供給部停止 → 通信部停止 → CSV 保存」の順です。`q` / Ctrl+C / ディスアームで通常どおり終了できます。

#### 3.1.2 別ポート（USB）で `send_GPS3.py` と同時に動かす

§3.1.1 の「2 プロセスが同じポートを開くため成立しない」は、`send_GPS3.py` の接続先を USB に変えると解消できます。
`send_GPS3.py` は `--device` / `--baud` / `--rtscts` / `--no-rtscts` / `--url` を受け付けます（既定は従来どおり
`/dev/ttyAMA0` @1,000,000 bps・RTS/CTS 有効なので、引数なしの起動は今までと同じです）。

| プロセス | 接続先 | 起動例 |
|---|---|---|
| `send_GPS3.py`（GPS_INPUT 15Hz） | USB `/dev/ttyACM0`（推奨は `/dev/serial/by-id/...`） | `python3 send_GPS3.py --device /dev/ttyACM0 --baud 115200 --no-rtscts` |
| `AR-hook1.py`（ArUco 誘導） | TELEM1 `/dev/ttyAMA0` | `AR_HOOK_TARGET_YAW_DEG=180.0 python3 AR-hook1.py`（対話 1 で `1`） |

- 起動ログの `GPS_INPUT 送信先: /dev/ttyACM0 (baud=115200, rtscts=False)` で実際の接続先を確認する。
- `AR_HOOK_GPS_INPUT_ENABLE` は **0（既定）** のまま。`1` にすると AR-hook も GPS_INPUT を送り、**二重送信**になる。
- USB の ACM 番号は再起動で変わることがあるため `/dev/serial/by-id/...` で固定する。
  `sudo fuser -v /dev/ttyACM0 /dev/ttyAMA0` で他プロセスが掴んでいないことを確認する（`mavlink-bridge` は起動しない）。
- **`setup_AR-hook1.py`（実装済み）は `auto` で USB を優先**するため、USB 運用中のパラメータ投入・照合は
  `python3 setup_AR-hook1.py --check --device /dev/ttyAMA0` のように明示するか、AR-hook を止めてから実行する。
- この構成の実機確認は **NOT RUN**（§11.3 の B 案 = 次点。USB 抜け・ACM 番号変動は新しい故障点）。

### 3.2 3 つの対話（タイムアウトと既定値）

`input_with_timeout()` は「プロンプト表示 → 指定秒だけ待つ → 入力が無ければ既定値」という動作です。
**待つ前に標準入力バッファをフラッシュする**ため、事前に打ち込んだ改行などは捨てられます。
選択肢は**完全一致**で判定します（対話 1 は `1` / `2` / `3` 以外を打つと `❌ 接続設定エラー` で終了します）。

| 対話 | 内容 | 選択肢 | タイムアウト | 既定 | タイムアウト／想定外入力のとき |
|---|---|---|---|---|---|
| 1 | 接続方法 | `1`: Serial `/dev/ttyAMA0`, 1,000,000 bps, RTS/CTS 有効（推奨）<br>`2`: USB `/dev/ttyACM0`, 115,200 bps（RTS/CTS なし）<br>`3`: SITL `udpin:0.0.0.0:14550`（UDP。`--sitl` / `AR_HOOK_SITL=1` でも選択可。[SITL_SETUP.md](./SITL_SETUP.md)） | **5 秒** | `1`（Serial） | タイムアウトは Serial。`1`〜`3` 以外はエラー終了 |
| 2 | カメラ向き（姿勢）ソース | `1`: Motive（カメラ rigid body ID=3）<br>`2`: ArduPilot IMU（Pixhawk の姿勢＝MAVLink `ATTITUDE`） | **10 秒** | `1`（Motive） | Motive になる |
| 3 | 映像出力 | `1`: 本体画面（ウィンドウ表示＋MP4 記録）<br>`2`: なし<br>`3`: SSH ブラウザ配信 `http://127.0.0.1:8765` | **15 秒** | `2`（なし） | 「なし」になる |

タイムアウト時は次の行が出ます。

```
[タイムアウト] 5秒間入力がなかったため、デフォルト値 '1' を使用します。
```

#### 対話の順序と「自動離陸と重なる区間」

```
起動
 ├ 対話1（接続方法, 最大5秒）→ MAVLink 接続 → HEARTBEAT 待ち（最大10秒）
 │                              → 受信周期要求（24/33/30）
 ├ 対話2（姿勢ソース, 最大10秒）
 ├ ★ monitor_vehicle / record_data / Motive受信 の3スレッド開始
 │     ← ここから GUIDED＋アームを検出できる（既定では自動離陸しない）
 ├ 対話3（映像出力, 最大15秒）
 └ キーボード制御スレッド開始（control_loop, 50ms 周期）→「スペース」で離陸
```

- 既定（`AR_HOOK_AUTO_TAKEOFF=0`）では、**アームしても離陸しません**。対話が終わってキーボード制御が始まり、
  スペースキーを押したときに初めて離陸指令が出ます。
- `AR_HOOK_AUTO_TAKEOFF=1` のときだけ、従来どおり「GUIDED＋アームから 3 秒後」に自動離陸します。
  その場合は**対話 3 の待機中（最大 15 秒）にも自動離陸の判定が生きている**ため、アームは対話が終わってから行ってください。

```
✓ AR計測レート上限を40Hz（25000μs/frame）に設定しました。
✓ マーカー追跡ループを開始します（中心ID: 1, 正方形頂点ID: [2, 3, 4, 5]）...
```

**HEARTBEAT は 10 秒でタイムアウトし、そのまま終了します**（`sys.exit(1)`）。
メッセージは `❌ ハートビートの受信タイムアウト: Pixhawkからの応答がありません。` です（§11 参照）。

### 3.4 映像出力の選択と記録の関係

| 選択 | 画面 | MP4 | SSH 配信 |
|---|---|---|---|
| `1: 本体画面` | `cv2.imshow` のウィンドウ（`AR Camera`）。ディスプレイか X 転送が必要 | **記録する**（`~/LOGS_Pixhawk6c/<日時>_video.mp4`） | なし |
| `2: なし` | なし | 記録しない | なし |
| `3: SSH ブラウザ配信` | PC 側ブラウザ（SSH ポート転送） | **記録しない** | `127.0.0.1:8765` |

PC 側のポート転送例（起動ログにも同じ例が出ます）:

```bash
# その後ブラウザで http://127.0.0.1:8765/ を開く
```

配信は JPEG を約 10 Hz（0.1 秒間隔）で更新し、解像度は 820×616 に縮小されます（追跡・記録のレートは変わりません）。
ポートを開けない場合は `⚠ SSH映像配信を開始できません (...)` と出て「なし」で続行します。

## 4. 起動後の実挙動（コードと一致させた動作説明）

### 4.1 受信周期の要求（起動時に 1 回だけ）

`set_msg_rate(comm)` が `MAV_CMD_SET_MESSAGE_INTERVAL` を送ります。周期を決めるのはこの 1 箇所だけです。

| メッセージ ID | 名前 | 要求周期 [µs] | 周波数 |
|---|---|---|---|
| 24 | `GPS_RAW_INT` | 200,000 | 5 Hz |
| 33 | `GLOBAL_POSITION_INT` | 200,000 | 5 Hz |
| 30 | `ATTITUDE` | 25,000 | **40 Hz**（統合後の値） |

- `ATTITUDE` を 40 Hz にした理由は、カメラ計測を 40 Hz で回すためです（5 Hz では姿勢が最大 200 ms 古くなる）。
- 受信そのものは通信部のスレッド 1 本が行い、`monitor_vehicle()` は 5 ms 周期で最新値キャッシュの `seq` 変化だけを見ます。
- リンクは **3 秒間メッセージが来ないと切断とみなし**、`❌ MAVLinkリンク切断を検出 → プログラムを終了します` で終了します（CSV は保存されます）。

### 4.2 離陸のシーケンス（既定＝スペースキー／オプトイン＝自動離陸）

**既定（本運用）: スペースキー離陸**

| 段階 | 条件 | 動作 | ログ |
|---|---|---|---|
| 1 | `HEARTBEAT` で `custom_mode == 4` かつ armed、かつ直前まで Guided でなかった | GUIDED と armed を確定し、`vehicle_armed_confirmed=True` | `✓ Guidedモード検出 → 離陸準備`<br>`ℹ 自動離陸は無効です（AR_HOOK_AUTO_TAKEOFF=デフォルト）。スペースキーで離陸してください（目標 1.5m）` |
| 2 | キーボードでスペース（`" "`）を押す（確定 GUIDED かつ確定 armed のときだけ） | `MAV_CMD_NAV_TAKEOFF`（param7 = 1.5 m）を **1 回だけ**送信 | `✓ スペースキーで離陸指令（1.5m） — 床（EKF home）から 1.5m まで自動上昇します` |
| 3 | `GLOBAL_POSITION_INT.relative_alt >= 1.35 m`（1.5 × 0.9） | 追従目標の送信を許可し、目標 Down を「home＋1.5 m」に初期化 | `✓ 離陸高度到達: home相対 1.50m (target Down=...)` |
| 4 | Guided 中かつ段階 3 完了 | 以後はキーボード（u/m/h/l/w/z）とカメラ追従で移動 | `KEY: ...` / `[Tracker]` 行 |

- スペースを押し続けても 2 回目以降は `ℹ スペース離陸: 送信済みです（1.5m、再送しません）` を出すだけで、指令は送りません。
- GUIDED でない・未 armed のときは送らず、理由を 1 行表示します。
- 段階 3 の判定は**離陸地点（EKF home）からの相対高度**です。`GLOBAL_POSITION_INT` が来ていないと到達判定は進みません。
- 離陸地点の Down は最初の `GLOBAL_POSITION_INT` で決まり、`✓ 離陸地点のREF座標: X=..., Y=..., Down=...` と表示されます。これが確定するまでキー操作の送信も行われません。
- Guided から外れると `takeoff_sent` / `takeoff_reached` / `initial_target_set` はリセットされます（スペース送信済みフラグはリセットしません）。

**オプトイン: 自動離陸（`AR_HOOK_AUTO_TAKEOFF=1` のときだけ。本運用では使いません）**

| 段階 | 条件 | 動作 | ログ |
|---|---|---|---|
| 1 | GUIDED + armed を検出 | 離陸準備のタイマー開始 | `✓ Guidedモード検出 → 離陸準備` |
| 2 | 上記から 3 秒経過後の最初の `HEARTBEAT` | `MAV_CMD_NAV_TAKEOFF`（param7 = `TAKEOFF_ALT`、既定 1.5 m）を送信 | `✓ 離陸指令（1.5m）` |
| 3 | `relative_alt >= 1.35 m`（1.5 × 0.9） | 追従目標の送信を許可 | `✓ 離陸高度到達: home相対 1.50m` |

- 段階 2 は `HEARTBEAT` 受信を契機に評価するため、実時間では 3〜4 秒後になります。
- GUIDED を解除すると `takeoff_sent` がリセットされるため、**アームしたまま GUIDED へ入り直すと再び 3 秒後に離陸指令が出ます**（この挙動が危険なので既定は無効です）。

### 4.2.1 離陸後に自動で開始位置へ移動する（任意）

**本運用では使いません**（離陸後の移動はオペレータがキーボードで行います）。
`AR_HOOK_AUTO_START=1` を付けたときだけ、離陸高度到達後に開始位置
（既定 `36.0757693, 136.2132945`、離陸地点から 1.50 m）へ自動移動し、到着後に
カメラ追従（TRACK）を開始します。既定は無効で、従来どおり離陸後すぐ追従です。
SITL 検証（`verify_sitl.py --only auto_start`）と回帰テスト（`test_auto_start.py`）は維持しています。

期待ログ: `✓ 自動移動を開始します: 開始位置 N=... E=... 高さ=1.50m` →
`✓ 自動移動 到着: 水平距離 ... → カメラ追従を開始します` →
`✓ 自動移動フェーズ: TRACK`。30 秒で到着しない場合は
`⚠ 自動移動がタイムアウト...現在の目標を保持します` が出て移動だけを中止します
（降下・着陸はしません）。GUIDED 解除・disarm・リンク切断でも即中断します。

### 4.3 追従目標の送信レート

- setpoint は「1 枚のカメラフレームを処理するごとに最大 1 回」送ります。フレームレートは 40 Hz に設定されているため、**上限は 40 Hz** です。
- 送信条件は「Guided 中」「離陸高度到達済み」「離陸地点の Down が有限」の 3 つです。
- キーボード操作は 50 ms 周期で入力を監視し、**キーを押したときに 1 回**送ります（連打で増えます）。
- マーカーを見失ったときは、1.0 秒までは直前の目標を保持し、その後 0.15 m/s で現在位置（水平）へ戻ります（高度は保持）。この間も同じフレーム周期で setpoint を送り続けます。
- ヨーは毎回 `TARGET_YAW_SEND_DEG`（`AR_HOOK_TARGET_YAW_DEG` ＋ 取付ヨーオフセット）の固定値です。

**定期再送（GUID_TIMEOUT 対策 / `AR_HOOK_SETPOINT_RESEND_HZ`、既定 5Hz = 0.2 秒周期）**

- キー入力もカメラ検出も無い間（手動キー運用の待機中・離陸直後）は、キーボードスレッド
  （`control_loop`）が **現在の target を 0.2 秒ごとに再送**します。target は書き換えません
  （クランプ済みの値をそのまま送るだけ）。
- カメラが 40Hz で送っている間、およびキーを押した直後（0.2 秒以内）は再送しません
  （同じ目標の二重送信をしない）。**カメラ経路の 40Hz は従来どおり**です。
- 送信可否はカメラ・キーと同じ判定（GUIDED かつ離陸高度到達後、home 高度確定）です。
  GUIDED 以外・未離陸・home 未確定では送りません。
- **`GUID_TIMEOUT` との関係**: 0.2 秒周期は現行 `GUID_TIMEOUT=3.0 s` の 1/15、
  `setup_AR-hook1.py` が投入する 30.0 s の 1/150 です。再送が 1〜2 回失敗しても
  3.0 s 以内に 14 回以上送れるため、キーから手を離しても GUIDED の目標タイムアウトは
  成立しません。タイムアウトが問題になるのは **AR-hook を止めた後**（`q` / Ctrl+C /
  リンク切断 / 電源断）だけです（[FAILSAFE_CHECKLIST.md](./FAILSAFE_CHECKLIST.md) §5.1）。
- `AR_HOOK_SETPOINT_RESEND_HZ=0` で無効にすると、従来どおり「キーを押した瞬間」と
  「カメラ検出中（40Hz）」だけの送信に戻ります（範囲 0〜20、範囲外は起動時エラー）。

### 4.4 姿勢が古いときの自動追従停止（stale）

- しきい値は既定 **100 ms**（`ARHOOK_ATTITUDE_STALE_TIMEOUT_MS` で変更）。
- 判定対象になるのは「目標計算に MAVLink `ATTITUDE` を使う経路」だけです。
  - 対話 2 で `2: ArduPilot IMU` を選んだ場合 → **常に判定対象**。
  - 対話 2 で `1: Motive` を選び、そのフレームのカメラ rigid body（RB3）姿勢が補間できた場合 → **判定対象外**（Motive 姿勢で変換するため）。
  - `1: Motive` でも RB3 姿勢が無く、RB1（機体）姿勢も未受信の場合 → `ATTITUDE` へフォールバックし、**判定対象**。
- しきい値を超えると、`commit_target_command()` を呼ばず **setpoint も送りません**（前回の目標を保持）。警告は 1 秒に 1 回です。

```
⚠ MAVLink ATTITUDE が古いため自動誘導目標の更新を停止し、前回目標を保持します (age=152ms, しきい値=100ms, source=motive)
```

- CSV の `Attitude_Age_ms`（最終受信からの経過時間、未受信は nan）と `Attitude_Stale`（古い/未受信なら 1）で後から確認できます。
- 注意: この停止は**自動追従だけ**です。キーボード操作は stale の影響を受けません。

### 4.5 目標のクランプ・レート制限（統合後の変更点）

目標の書き換えは `commit_target_command()` の 1 箇所に集約されています。

| パラメータ | 既定値 | 意味 |
|---|---|---|
| `TARGET_MAX_SPEED_MPS` | 0.50 m/s | 目標指令の最大移動速度 |
| `TARGET_MAX_STEP_M` | 0.0125 m（= 0.50 / 40 Hz） | 1 フレームあたりの最大移動量 |
| `TARGET_MAX_OFFSET_M` | 1.20 m | 現在位置から目標までの水平最大偏差（半径） |
| `TARGET_MAX_ALT_UP_M` | 0.30 m | 上昇方向の最大偏差 |
| `TARGET_MAX_ALT_DOWN_M` | 0.20 m | 下降方向の最大偏差 |
| `TARGET_LOST_HOLD_S` | 1.00 s | 検出ロスト時に目標を保持する時間 |
| `TARGET_LOST_DECAY_MPS` | 0.15 m/s | 保持時間超過後に現在位置へ戻る速度 |

- 適用順序は「偏差クランプ → レートリミット」です。
- **レートリミットはカメラ追従だけ**に掛かります。キーボードの 1 回 0.10 m は分割されません（押した分だけ動く）。
- クランプはキーボードにも掛かるため、現在位置から上限を超える操作は頭打ちになります。
- 動作状況は CSV の `Target_Desired_*` / `Target_Limit_*` / `Target_Hold_*` / `Target_Update_Source` で確認できます（§7.1）。

### 4.6 送信の排他（統合後の変更点）

- 送信はすべて [mavlink_comm.py](./mavlink_comm.py) の薄い API（`setpoint` / `takeoff` / `command_long` / `set_message_interval`）を経由し、通信部内部の `_send_lock` で直列化されます。
- `AR-hook1.py` 側に送信ロックはありません（二重ロックにしない構成）。
- 取得順序は「`io_lock` → 通信部 `_send_lock`」の一方向のみです。`io_lock` を保持したまま送信しない規約になっています。

## 5. キーボード操作

`control_loop()` は 50 ms 周期で 1 文字ずつ読みます（Enter 不要）。`q` 以外は**押した瞬間に 1 回**だけ目標を動かします。

**キーと NED の対応（重要）**: キーは NED ローカル座標（`x`=北、`y`=東、`z`=Down）を直接動かします。
機首は `TARGET_YAW_SEND_DEG` で固定（既定 `0.0°` ＝ 北）なので、**機首を 180°（南）に固定している場合は
`m`（北）が機体にとって「後退」**になります。画面にも同じ対応表が出ます。

| キー | 動作 | 内部の変化 | 備考 |
|---|---|---|---|
| `SPACE` | **離陸** | `MAV_CMD_NAV_TAKEOFF`（`TAKEOFF_ALT`、既定 1.5 m）を 1 回だけ送信 | 確定 GUIDED かつ確定 armed のときだけ。押し続けても再送しない |
| `u` | 南（`-N`） | `x -= 0.10 m`（北成分を減らす） | GUIDED 中なら離陸前でも送信され得る |
| `m` | 北（`+N`） | `x += 0.10 m` | 同上。機首 180° 固定では「後退」 |
| `h` | 東（`+E`） | `y += 0.10 m` | 同上 |
| `l` | 西（`-W`） | `y -= 0.10 m` | 同上 |
| `w` | 上 | `z -= 0.10 m`（Down を減らす） | **高度到達後**のみ有効 |
| `z` | 下 | `z += 0.10 m`（Down を増やす） | 高度到達後。離陸地点から **0.05 m** を下回る操作は無効 |
| `t` | 基準点 | N/E を開始位置（既定 `36.0757693, 136.2132945`、`AR_HOOK_START_LAT/LON` で変更可）へ、高さを離陸地点から **1.50 m**（`AR_HOOK_START_HEIGHT_M`）に設定 | 高度到達後のみ有効。自動移動と同じ定義 |
| `q` | 終了 | ループを抜けてプログラム終了 | 機体へは何も送らない |

- 押すと次のように表示されます（移動キーは NED の変化も併記）。

```
KEY: m North (+N) → N=0.10 E=0.00 D=-1.50
✓ スペースキーで離陸指令（1.5m） — 床（EKF home）から 1.5m まで自動上昇します
ℹ スペース離陸: 送信済みです（1.5m、再送しません）
```

- キーボード操作は `commit_target_command()` → `can_send_guided_setpoint()` → `send_local_target()` の既存経路だけで送ります
  （クランプ 0.5 m/s・水平 1.20 m・上 0.30 m / 下 0.20 m を必ず通ります）。
- `w` / `z` / `t` は「離陸高度到達（`initial_target_set`）」まで無効です。押しても何も起きません。
- 離陸地点の Down が未確定のときは `⚠ 離陸地点の高度が未確定のため目標を送信しません` と表示され、送信されません。
- 映像出力で `1: 本体画面` を選んだ場合、ウィンドウ側の `q` キー（`cv2.waitKey`）でも終了します。
- キーボードの送信もカメラ経路と同じ `can_send_guided_setpoint()` を通ります。**GUIDED 以外では送信しません**（`⚠ Guidedモードではないため目標を送信しません`）。キーボードだけは離陸高度到達（`initial_target_set`）を条件にしません。

## 6. 実験の実施手順（全体シーケンス）

1. **準備**（§2 のチェックリスト 1〜8）— プロペラ、GPS、EKF、テザー、退避距離、ディスク。
2. **起動**（§3.1）— `AR_HOOK_TARGET_YAW_DEG` を決めてから実行する。モードはまだ GUIDED 以外。
3. **対話 1〜3 を完了**（§3.2）— タイムアウトさせずに明示的に入力することを推奨。
   - 特に映像出力は、MP4 が必要なら `1`、ヘッドレスでブラウザ確認だけなら `3`。
4. **受信確認**（§2 の 9・10）— `[Motive Pose UDP] Receiver thread started on port 15770`、
   `[Tracker]` 行の `IDs=` と `camera=received`、`AR=` の Hz。
5. **マーカーの見え方確認** — 荷物（ID2〜5）と機体側 ID1 が同時に映るか。
   ID1 が見えないときは荷物中心そのものを目標にするため、ねらいの位置が変わる。
6. **アーム → GUIDED へ切替**（送信機）
   - 既定では**離陸しません**。`✓ Guidedモード検出 → 離陸準備` のあとに
     `ℹ 自動離陸は無効です（AR_HOOK_AUTO_TAKEOFF=デフォルト）。スペースキーで離陸してください（目標 1.5m）`
     が出ることを確認します（自動離陸は `AR_HOOK_AUTO_TAKEOFF=1` のときだけ）。
7. **スペースキーで離陸**（パソコンのキーボード）
   - `✓ スペースキーで離陸指令（1.5m）` → 床から 1.5 m まで自動上昇 → `✓ 離陸高度到達: home相対 1.50m` を確認。
   - GUIDED / armed が確定していないと送信されません（理由が 1 行表示されます）。
   - 押し続けても再送しません（`ℹ スペース離陸: 送信済みです（1.5m、再送しません）`）。
8. **手動で実験開始位置へ移動**（キーボード）
   - `u`（南）/ `m`（北）/ `h`（東）/ `l`（西）で水平を 1 回 0.10 m ずつ、`w`（上）/ `z`（下）で高さを調整します。
     `t` を押すと基準点（開始位置・既定 1.50 m）へ戻ります。
   - **キーと NED の対応**は §5 の表を参照。機首を 180°（南）に固定している場合、`m`（北）は「後退」になります。
9. **追従開始** — `[Tracker]` 行が 1 Hz で出続け、`target-NED=` が更新されることを確認。
10. **終了** — 送信機で **GUIDED を解除 → 着陸 → ディスアーム**（§8 の表を参照）。
    ディスアームを検出するとプログラムは自動終了し、CSV を保存します。

```
ディスアーム検出 → running=False → カメラループ終了（MP4 release）
                 → comm.stop() → save_csv() → 「✓ プログラム終了」
```

9. **記録の確認** — `ls -l ~/LOGS_Pixhawk6c/` で `<日時>_1.csv`（と必要なら `<日時>_video.mp4`）を確認。

### 6.1 GUIDED 自動移動（`AR_HOOK_AUTO_START`）の実機手順と結果記入欄

`AR_HOOK_AUTO_START=1` を付けたときだけ、離陸高度到達後に開始位置へ自動移動し、到着してから
カメラ追従（TRACK）を開始します（動作の説明は §4.2.1）。**既定は無効**（`0`）で、
**本運用（スペースキー離陸＋キーボード移動）では使いません**（コードは残しており、SITL・回帰テストで維持）。
**アームと離陸を伴うため、実施可否は人間が判断します。実施しない場合は記入欄を `NOT RUN` のまま残します。**

#### 6.1.1 事前準備（§2 のチェックリストに追加して確認）

| # | 項目 | 確認内容 |
|---|---|---|
| A1 | 開始位置の座標 | `AR_HOOK_START_LAT` / `AR_HOOK_START_LON`（既定 `36.0757693` / `136.2132945`）が実際の実験開始位置と一致するか（GCS の地図で確認） |
| A2 | 開始位置の高さ | `AR_HOOK_START_HEIGHT_M`（既定 `1.50` m、離陸地点から）が周囲の障害物より高いか |
| A3 | 到着しきい値 | `AR_HOOK_AUTO_START_ARRIVE_XY_M`（`0.15`）/ `_Z_M`（`0.10`）/ `AR_HOOK_AUTO_START_ARRIVE_FRAMES`（`2`）。風があると到着しないことがある（30 秒でタイムアウト） |
| A4 | 移動経路 | 離陸地点 → 開始位置の間に障害物・人・テザーの干渉が無いか（接近は移動上限 0.50 m/s、クランプ・レート制限あり） |
| A5 | REF と離陸地点 | 離陸地点（EKF home）と Motive 原点は別。誤差評価は**同じ座標系の 2 点**で行う（§6.1.4） |
| A6 | 中止手段 | 送信機で GUIDED 解除 → 即停止できること（§8）。`q` はプログラム終了のみで機体は止めない |

#### 6.1.2 起動と実施手順

1. 起動（§3.1）に `AR_HOOK_AUTO_START=1` を足す（離陸は従来動作なので `AR_HOOK_AUTO_TAKEOFF=1` も足す）。

```bash
cd AR-hook
AR_HOOK_AUTO_TAKEOFF=1 AR_HOOK_AUTO_START=1 AR_HOOK_TARGET_YAW_DEG=0.0 python3 AR-hook1.py
```

2. 起動ログの `ℹ 離陸後の自動移動: 有効（AR_HOOK_AUTO_START=1、開始位置 lat=... lon=... 高さ=...m、
   到着 0.15m/0.10m を 2 フレーム連続、タイムアウト 30.0s）` を確認する（無効時は `無効（...=0、既定どおり
   離陸後すぐカメラ追従）`）。
3. 対話 1〜3 を完了し、`[Tracker]` 行で `IDs=` と `camera=received` を確認（§2 の 9・10）。
4. 送信機でアーム → GUIDED へ切替（`AR_HOOK_AUTO_TAKEOFF=1` なので **3 秒後に自動離陸**）。
5. 次の順にログが出ることを確認する。

```text
✓ Guidedモード検出 → 離陸準備
ℹ 自動移動フェーズ: TAKEOFF_WAIT（離陸高度到達を待ちます）      ← GUIDED+armed 検出時
✓ 離陸指令（1.5m）                                             ← AR_HOOK_AUTO_TAKEOFF=1
✓ 離陸高度到達: home相対 1.50m (target Down=...)
✓ 自動移動を開始します: 開始位置 N=... E=... 高さ=1.50m（現在の水平距離 ...m、移動上限 0.50m/s で接近）
✓ 自動移動 到着: 水平距離 ...m（しきい値 0.15m）、高さ差 ...m（しきい値 0.10m）、経過 ...s（2 フレーム連続） → カメラ追従を開始します
✓ 自動移動フェーズ: TRACK（カメラ追従を再開します）
```

6. 到着後は `[Tracker]` 行の `target-NED=` が更新され、CSV の `Target_Update_Source` が `camera` に
   なることを確認する（自動移動中はカメラ経路の目標更新を止めているため、`auto_start` のまま）。
7. 終了は §8 のとおり（送信機で GUIDED 解除 → 着陸 → ディスアーム）。

異常時の表示（いずれも移動だけを中止し、降下・着陸はしません）:

| 表示 | 意味 | 対応 |
|---|---|---|
| `⚠ 自動移動がタイムアウト（30.0秒）しました。移動を中止し、現在の目標を保持します...降下・着陸は行いません` | 30 秒で到着条件を満たさなかった | 記録して中止理由を残す。必要なら `t` キーで基準点へ戻すか送信機で解除 |
| `⚠ 自動移動を中断しました（理由: GUIDED 解除 / 終了要求 (running=False) / ...）` | GUIDED 解除・disarm・リンク断・終了 | §8 の中断手順に従う |

#### 6.1.4 誤差の測り方（Motive 真値との比較）

- 到着ログの `水平距離` / `高さ差` と CSV の `Auto_Start_Dist_m` は、**Pixhawk の `GLOBAL_POSITION_INT`
  を REF ローカル NED に変換した値**（`GPS_Drone_X/Y/Z_m`）で計算されています。
- Motive 真値は、**開始位置を Motive 座標で測った点**と、到着時点の `Motive_Drone_X/Y/Z_m`（RB1）の差で
  評価します。開始位置は Motive 上にマーカー等で印を付けるか、**離陸前に機体を開始位置へ置いて
  Motive を記録**しておきます。
- Motive と REF は原点が異なるため、**同じ座標系で測った 2 点の差**だけを記録します
  （`GPS_Drone_*` と `Motive_Drone_*` を直接引き算しない）。
- 高度は `Motive_Drone_Z_m` の差（Down 方向、+ が下降）で評価します。

## 7. 記録（CSV・映像）

### 7.1 CSV

- 出力先: `~/LOGS_Pixhawk6c/<YYYYMMDD_HHMMSS>_1.csv`
- ファイル名の日時は**保存した瞬間**（`Asia/Tokyo`）です。記録開始時刻ではありません。
- 保存は `main()` の `finally` から `save_csv()` が 1 回だけ行います。`✓ CSV保存完了: <パス> (<行数> 行)` が出れば成功です。
- 記録スレッドは **40 Hz**（`AR_LOG_HZ = 40`）で 1 行追記します（メモリ上に保持し、終了時に一括書き出し）。
- `Time_s` は `time.time()`（UNIX エポック秒）です。解析では先頭との差分を使ってください。

#### 主な列（すべてではありません。全列は `save_csv()` を参照）

| 列 | 意味 |
|---|---|
| `Time_s` | UNIX エポック秒 |
| `GPS_Drone_X/Y/Z_m` | REF 原点基準のローカル NED（N/E/D、単位 m）。起動時原点への正規化はしない |
| `Target_Drone_X/Y/Z_m` | 送信に使った目標（REF 基準ローカル NED、Down） |
| `Est_Cargo_X/Y/Z_m` | 推定した荷物中心（NED） |
| `Cargo_Detected` / `ID1_Detected` | 荷物（ID2〜5）／ID1 の検出フラグ（1/0） |
| `ID1_to_Cargo_DX/DY/DZ_m` | ID1 から荷物中心への相対量（カメラ座標系由来） |
| `Motive_Drone_*` / `Motive_Cargo_*` / `Motive_Rel_*` | Motive の機体（RB1）・荷物（RB2）位置と相対量 |
| `Motive_Camera_*`, `Motive_Camera_Received` | カメラ rigid body（RB3）位置と受信フラグ |
| `Motive_RB{1,2,3}_*` | 剛体ごとの姿勢・位置・パケット時刻・受信フラグ（`Pose_Received`） |
| `Coord_Source` | `Motive-Camera` / `IMU-Fallback` / `ArduPilot-Mag` |
| `Camera_Orientation_Source` | `motive` / `ardupilot`（対話 2 の選択） |
| `Pixhawk_Roll/Pitch/Yaw_rad` | MAVLink `ATTITUDE` の値 |
| `Attitude_Age_ms` / `Attitude_Stale` | ATTITUDE の鮮度（未受信は nan / 1） |
| `AR_Hand_*`, `AR_Cargo_*` | AR マーカーから求めた NED 位置・姿勢・時刻・受信フラグ |
| `AR_*_PreOffset_*` | マーカー姿勢オフセット適用前の値 |
| `Target_Desired_*`, `Target_Limit_*`, `Target_Hold_*`, `Target_Lost_Decay_Active`, `Target_Update_Source` | クランプ・レート制限・ロスト保持の作動状況。`Target_Update_Source` は `camera` / `keyboard` / `lost_hold` / `lost_decay` / `auto_start`（起動直後でまだ一度も更新していない行は `none`） |

### 7.2 映像（MP4）

- 出力先: `~/LOGS_Pixhawk6c/<YYYYMMDD_HHMMSS>_video.mp4`
- **映像出力で `1: 本体画面` を選んだときだけ**作られます（`2` / `3` では作られません）。
- 書き出しは「最初に表示したフレーム」の時点で始まり、`✓ ビデオ録画を開始しました: <パス>` と表示されます。
- コーデックは `mp4v`、FPS は `AR_MEASUREMENT_FPS = 40`、解像度はカメラの取り込みサイズ（1640×1232）です。
- 終了時に `video_writer.release()` が呼ばれ、`✓ ビデオ録画を終了しました。` と表示されます。
- **CSV と MP4 は別々の時刻で命名されます**（CSV は終了時、MP4 は録画開始時）。同じ実験のファイルを探すときは、更新時刻と内容で対応づけてください。

### 7.3 記録が残らないケース

| 状況 | CSV | MP4 |
|---|---|---|
| `q` / Ctrl+C / ディスアーム検出 / リンク切断 | 保存される | 保存される（`1` を選んでいれば） |
| カメラを開けずに追跡ループが即終了 | 保存される（行はごく少ない） | 作られない |
| `kill -9`（SIGKILL）/ 電源断 | **失われる** | 壊れる／失われる |
| `1` 以外の映像出力を選択 | 保存される | 作られない |

## 8. 中断手順

「何をしたときに、機体へ何が送られ、記録がどうなるか」の一覧です。
**本プログラムは機体を着陸・停止させる指令を送りません。** 機体を止める操作は必ず送信機側で行ってください。

| 操作 | プログラムの動き | 機体への指令 | 機体の挙動 | CSV | MP4 |
|---|---|---|---|---|---|
| **送信機で GUIDED 解除**（LOITER / LAND 等へ） | `HEARTBEAT` で `guided_mode_active=False` を反映。カメラ追従とロスト時の setpoint 送信が止まる。離陸状態（`takeoff_sent` 等）はリセットされ、プログラムは**動作継続** | 新規 setpoint は送らない（キーボードも GUIDED 判定で遮断される） | 選んだモードの挙動。本プログラムは関与しない | 継続して記録。`Target_Update_Source` の更新が止まる | 継続（`1` 選択時） |
| **ディスアーム**（送信機） | `✓ ディスアーム検出` → `running=False` → ループ終了 → `comm.stop()` → `save_csv()`。**自動終了** | 何も送らない | 送信機のディスアーム操作そのもの。モータ停止 | **保存される** | **保存される**（release 実行） |
| **`q` キー**（端末／ウィンドウ） | `running=False` → 同上の終了処理。**自動終了** | 何も送らない（着陸・ディスアーム指令なし） | 最後に受け付けた目標を保持し続ける（ArduPilot 側の GUIDED の扱いによる）。**送信機で解除するまで飛び続ける可能性がある** | **保存される** | **保存される** |
| **Ctrl+C**（SIGINT） | `KeyboardInterrupt` を捕捉し、`finally` で `comm.stop()` → `save_csv()`。**自動終了** | 何も送らない | 同上 | **保存される** | **保存される**（`finally` で release） |
| `kill`（SIGTERM）/ `kill -9`（SIGKILL） | `finally` が実行されない | 何も送らない | 同上 | **失われる**（SIGKILL/SIGTERM とも保存処理に到達しない） | 壊れる／失われる |
| **リンク切断**（3 秒無受信） | `❌ MAVLinkリンク切断を検出 → プログラムを終了します` で終了し、CSV を保存 | 送信もできなくなる | 機体側はフェールセーフ設定に従う | **保存される** | **保存される** |

補足:

- 「ディスアーム検出」は **armed → disarmed の遷移**でのみ働きます。一度もアームしていない場合は検出されず、プログラムは終了しません。
- `q` / Ctrl+C のあとに**必ず** `✓ CSV保存完了: ...` が出たことを確認してください。出ていない場合は記録が残っていません。
- Ctrl+C はメインスレッド（カメラ追跡ループ）に届きます。カメラ追跡ループの `finally` が MP4 を release してから、`main()` の `finally` が CSV を保存します。
- 緊急時はプログラムの終了を待たず、**送信機で GUIDED 解除 → 着陸 → ディスアーム**を優先してください。CSV はディスアーム検出後に自動保存されます。

## 9. ベンチと実機の違い

| 項目 | ベンチ（プロペラ外し／拘束） | 実機 |
|---|---|---|
| 目的 | ログ経路・座標変換・キー操作・stale 判定の確認 | 追従性能の評価 |
| プロペラ | **必ず外す**か機体を確実に拘束する | 取付・増し締めを確認（§2 No.1） |
| スペースキー離陸 | `MAV_CMD_NAV_TAKEOFF`（1.5 m）は**ベンチでも送られる**。プロペラを外していてもモータは回る | そのまま 1.5 m まで上昇する |
| 自動離陸（任意） | `AR_HOOK_AUTO_TAKEOFF=1` のときだけ、GUIDED＋アーム 3 秒後に 1.5 m の離陸指令が送られる | 同左。**本運用では使わない** |
| 高度到達判定 | `relative_alt >= 1.35 m`（1.5 × 0.9）に到達しないと追従目標の送信が始まらない。機体を吊るす／Motive で GPS を供給するなどして高度を成立させる必要がある | 実際に 1.5 m まで上昇する |
| GPS | 屋内では Motive の位置を `GPS_INPUT` として供給する。**推奨は AR-hook 自身**（`AR_HOOK_GPS_INPUT_ENABLE=1`）。`send_GPS3.py` は同時に起動しない（1 ポート運用） | 屋外なら通常の GPS。3D fix を確認 |
| カメラ | 手で動かしてマーカーを映す。USB カメラでも可（`SensorTimestamp` が無いためフレーム時刻は取得完了時刻になり、Motive との時刻同期精度は落ちる） | Picamera2（40 Hz・センサ時刻）を推奨 |
| Motive | RB3 が無いと `IMU-Fallback` になる。`Attitude_Stale` が立つと自動追従が止まる | RB1/RB2/RB3 をすべて受信させる |
| 映像記録 | ヘッドレスなら `3`（SSH 配信）。MP4 が必要ならディスプレイ／X 転送＋`1` | 同左 |
| 解析 | `Coord_Source` が `IMU-Fallback` でも経路の確認はできる | `Motive-Camera` の割合を評価に使う |
| 危険 | プロペラ・テザーで管理。それでもアームは最小限 | §0.1 の自動離陸がそのまま危険になる |

ベンチで確認しておくと実機が楽になる点:

1. 対話 1〜3 のタイムアウト既定値（5 / 10 / 15 秒）どおりに動くか。
2. スペースキーで `✓ スペースキーで離陸指令（1.5m）` が出るか（モータを回したくない場合はプロペラを外す）。
   `AR_HOOK_AUTO_TAKEOFF=1` のときだけ、`✓ 離陸指令（1.5m）` が GUIDED＋アームから約 3 秒後に出る。
3. キーボード `u/m/h/l/w/z/t` のログ（`KEY: ...`）と `Target_Drone_*` の変化が一致するか。
4. `Attitude_Stale` が 0 のままか、`Coord_Source` が期待どおりか。
5. `✓ CSV保存完了` と MP4 の有無（`1` を選んだときだけ作られる）。

- 内容: 位置は「AR 補正前 / AR 補正後 / Motive」の比較、姿勢は「AR 補正後 / Motive」の比較。
- Motive 姿勢の補間は最大 0.1 s ギャップまでです（定数 `POSE_INTERPOLATION_MAX_GAP_S`）。
- 横軸は「CSV 先頭からの経過秒」で、既定では **10〜200 秒**に固定されています（`PLOT_X_RANGE_S = (10, 200)`）。実験がこれより短い／長い場合は、スクリプト冒頭の定数を編集してください。

### 10.4 カメラ光学中心オフセットの校正（必要なときだけ）

```bash
cd AR-hook
# まずは既存ファイルを触らない出力先で試す
python3 calibrate_camera_optical_offset.py \
  ~/LOGS_Pixhawk6c/20261118_101530_1.csv \
  --source motive \
  --output /tmp/camera_extrinsics.json \
  --marker-output /tmp/marker_pose_offsets.json
```

- 引数: CSV は複数指定できます（姿勢の多様性を確保するため複数ログ推奨）。`--source` は `motive`（既定）または `ardupilot`。
- 既定の出力先はスクリプトと同じフォルダの `camera_extrinsics.json` と `marker_pose_offsets.json` です。
- **既存ファイルがある場合は `--force` を付けないとエラーで停止します**（`既存ファイルを上書きするには --force を指定: ...`）。
- `--source ardupilot` のときは `camera_extrinsics.json` のみを書き、`marker_pose_offsets.json` は更新しません。
- 安全弁: `--max-rmse-m`（既定 0.05 m）を超える推定は採用しません。`--max-offset-norm-m`（既定 1.0 m）を超えるレバーアームは「もっともらしくない」として失敗します。`--max-time-gap-ms`（既定 100）で同期の許容差を決めます。
- 校正サンプルが不足すると `...の姿勢校正サンプルが不足しています` で停止します。
- 実行後は AR-hook を再起動すると新しい `camera_extrinsics.json` / `marker_pose_offsets.json` が読み込まれます（起動ログに `✓ カメラ光学中心の外部オフセットをロードしました` / `✓ ARマーカーとMotive剛体の固定姿勢オフセットをロードしました` が出ます）。

### 10.5 確認すべき列

| 見たいこと | 列 | 見方 |
|---|---|---|
| 記録レートが 40 Hz か | `Time_s` | 差分が約 0.025 s か。欠けている区間がないか |
| 荷物を検出できていたか | `Cargo_Detected`, `ID1_Detected` | 1 の割合。追従区間で 0 が続いていないか |
| 誰が目標を更新したか | `Target_Update_Source` | `camera` が主か。`lost_hold` / `lost_decay` が多い時間帯はマーカーを見失っている |
| クランプ・レート制限の作動 | `Target_Limit_Rate_Active`, `Target_Limit_XY_Clamp_Active`, `Target_Limit_Z_Clamp_Up/Down`, `Target_Limit_Invalid` | 1 が多いときは目標が物理上限に張り付いている（誤差注入を疑う） |
| 目標と機体の関係 | `GPS_Drone_*` と `Target_Drone_*` | 差が `TARGET_MAX_OFFSET_M`（1.20 m）以内か。高度差が想定内か |
| 座標変換の経路 | `Coord_Source` | `Motive-Camera` が理想。`IMU-Fallback` が多いときは RB3 未受信／時刻同期ずれ |
| 姿勢の鮮度 | `Attitude_Age_ms`, `Attitude_Stale` | 目標更新中の `Attitude_Stale=1` は自動追従停止を意味する |
| Motive の受信状況 | `Motive_Camera_Received`, `Motive_RB{1,2,3}_Pose_Received` | 追従区間で 1 が続いているか |
| AR の姿勢品質 | `AR_Hand_*`, `AR_Cargo_*`（位置・クォータニオン・`Pose_Received`） | `Pose_Received=0` の区間はフレーム姿勢が補間できていない |
| 同期の基準 | `AR_*_Camera_Pose_Time_s`, `Motive_RB3_Pose_Time_s` | 補間が成立しているか（解析スクリプトの前提） |
| ヨーが固定どおりか | 送信値そのものは CSV に無い | 起動ログの `ℹ 目標ヨー:` と `Camera_Orientation_Source`、機体の実際の向き（Motive/Pixhawk 姿勢列）で確認 |

## 11. トラブルシュート

| 症状 | ログの目印 | 主な原因 | 対処 |
|---|---|---|---|
| **HEARTBEAT タイムアウト** | `❌ ハートビートの受信タイムアウト: Pixhawkからの応答がありません。` で終了 | 配線（TX/RX）、ボーレート不一致、Pixhawk の電源/起動前、`/dev/ttyAMA0` を他プロセスが占有、USB 未接続 | 対話 1 の選択を見直す（Serial 1,000,000 RTS/CTS / USB 115,200）。`ls -l /dev/ttyAMA0 /dev/ttyACM0` と `SERIAL1_BAUD` を確認。`mavlink-bridge` 等がポートを掴んでいれば停止する |
| **Motive 未受信（RB3 が N/A）** | `⚠ 撮影時刻に対応するMotive RB3姿勢を補間できません。frame=..., RB3履歴=[...], 待機=50ms, 許容サンプル間隔=0.100s。` / `[Tracker]` の `camera=N/A` | Motive が送っていない、ポート違い（15770）、剛体 ID 違い（1/2/3）、PC と Pi のセグメント違い、時計ずれ | Motive 側で剛体 ID を 1=機体, 2=荷物, 3=カメラに設定し、UDP 15770 へ送る。`sudo tcpdump -ni any udp port 15770` で着信確認。時計を合わせる（NTP 等）。受信できない間は `Coord_Source=IMU-Fallback` になり動作は継続する |
| **カメラ未検出** | `❌ エラー: カメラを開けませんでした。追跡スレッドを停止します。` → 追跡ループ終了 → そのまま終了 | カメラ未接続、Picamera2 の起動失敗＋USB カメラ無し、`/dev/video*` の権限 | リボンケーブル・`libcamera` を確認。カメラ単体の動作確認（例: `libcamera-hello` / `rpicam-hello`）を行う。USB カメラなら `ls -l /dev/video*`。※この場合 CSV は保存されるが行数はごく少ない |
| **姿勢 stale 警告** | `⚠ MAVLink ATTITUDE が古いため自動誘導目標の更新を停止し、前回目標を保持します (age=..., しきい値=100ms, source=...)` | `ATTITUDE` が届いていない、レート不足、`ardupilot` モードで 40 Hz が通っていない、RB3 が落ちてフォールバック中 | `Attitude_Age_ms` が 100 ms 未満か確認。ストリームレート設定を見直す。RB3 を受信させる。やむを得ない環境では `ARHOOK_ATTITUDE_STALE_TIMEOUT_MS` を 200 などに緩める（誤誘導リスクとのトレードオフ） |
| **送信レート不足（追従がカクつく）** | `[Tracker] AR=18.5/40.0Hz` のように 40 Hz より低い、`Target_Update_Source=camera` の行がまばら | CPU 飽和（1640×1232＋ArUco）、USB カメラの実 FPS 不足、RB3 補間待ち（1 フレーム最大 50 ms）、UART 帯域 | `top` で CPU を確認。USB カメラは `USBカメラ申告FPS:` を確認。解像度を下げる／他プロセスを止める。RB3 未受信なら Motive 側を直す。setpoint は「フレームごと」なので、フレームレートが上がらないと送信レートも上がらない |
| **リンク切断（3 秒無受信）** | `❌ MAVLinkリンク切断を検出 → プログラムを終了します` | ケーブル抜け、Pixhawk 再起動、ポート競合、電源 | 復旧して再起動。CSV は保存済み。機体側はフェールセーフ設定に従う |
| **MP4 が無い** | — | 映像出力で `2` / `3` を選んだ、または `1` だがウィンドウを開けず終了 | MP4 が必要なら `1` を選び、ディスプレイまたは X 転送を用意する（`3` は配信のみで記録しない） |
| **`1: 本体画面` で落ちる** | OpenCV のウィンドウ関連エラー | ヘッドレス環境（`DISPLAY` なし） | ヘッドレスでは `3` を選ぶ。MP4 が必須なら X 転送（`ssh -X`）か仮想ディスプレイを使う |
| **`ArUco: detectMarkers (OpenCV 4.6 互換)` が出る** | 起動直後の 1 行（正常）。`❌ ArUco ディテクタを初期化できません` が出た場合のみ異常 | Debian 12 の `python3-opencv`（OpenCV 4.6）には `ArucoDetector` / `DetectorParameters()` が無い | ArucoDetector が無い環境では `aruco.detectMarkers` に自動フォールバックする（対応 4.6〜5.x、コード変更は不要）。初期化失敗時は `python3 -c "import cv2; print(cv2.__version__)"` で版を確認する |
| **キーが効かない** | `KEY: ...` が出ない | 端末以外（バックグラウンド実行・リダイレクト）で起動、`stdin` が TTY でない | 端末フォアグラウンドで実行する。`w`/`z`/`t` は高度到達前は無効（仕様） |
| **環境変数で停止** | `❌ 環境変数 AR_HOOK_TARGET_YAW_DEG の値が範囲外です: ...` | 範囲外・数値でない（yaw は 0〜360、mask は 0〜0xFFFF） | 値を修正して再起動 |
| **送信が混線する／フレームが壊れる** | — | 通信部を迂回した送信の追加、`io_lock` 保持中の送信 | 送信は必ず `mavlink_comm` の API 経由にする（[ファイル概要.md](./ファイル概要.md) の「MAVLink送信のスレッド排他」）。[test_mavlink_comm.py](./test_mavlink_comm.py) / [test_mav_send_lock.py](./test_mav_send_lock.py) で検出できる |
