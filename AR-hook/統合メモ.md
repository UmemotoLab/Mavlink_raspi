## 4. 統合時に確認した整合性

1. **原点・高度基準（f6152）とクランプ上限（7f03b）**
   - クランプは `target` / `gps_now` と同じ REF 原点基準の NED（x=北, y=東, z=下）で計算します。
   - 送信時の home 相対高度への変換は `send_local_target()` → `local_down_to_home_relative_alt()` の 1 経路だけです。
   - キーボード `z` の下限は「離陸地点から 0.05 m」（f6152 の意味）を維持し、`t` キーも `alt_above_home_to_local_down()` を使います。7f03b の `commit_target_command()` 集約と両立しています。
2. **`send_setpoint` の yaw 引数化（9c2a5）と送信ロック（95501 / 通信部移行）**
   - `send_setpoint(comm, lat_i, lon_i, alt, yaw_deg=None)` は yaw を `math.radians()` で事前計算し、`comm.setpoint(..., yaw_rad=..., type_mask=MASK)` を呼びます。yaw の設定値は `TARGET_YAW_SEND_DEG`（環境変数で変更可）です。
   - **送信ロックは `MavlinkComm._send_lock` の 1 本だけ**です。`AR-hook1.py` には `mav_send_lock` を置かず、`m.mav.*_send` も直接呼びません（送信ロックが二重にならない構成）。
   - 62a00 の統合時は「`mav_send_lock` を本体側に残し、通信部の `_send_lock` と 2 段にする」版でしたが、**ブランチ側（`ca40f48`）の設計＝通信部 1 本を正**とします。
3. **ATTITUDE 40Hz（12794）と通信部の `set_message_interval`（e22e3）**
   - `set_msg_rate(comm)` は `24`/`33` を 200,000µs、`30` を 25,000µs で **各 1 回だけ**要求します。同じ ID に異なる周期を送る二重要求はありません。
4. **ロック取得順序**
   - 全コードで `io_lock` → 通信部 `_send_lock` の一方向のみです。`io_lock` 保持中の送信呼び出し、`_send_lock` 保持中の `io_lock` 取得は 0 件（AST 検査）。

## 6. 実機に載せる際の注意

1. **未 push のまま使う**: `feature/arhook-fixes` を checkout して実機に載せます。`git push` / `git push --force` / `git tag` は行わず、`main` は `1c6aca1` のまま動かしません。投入前に `git symbolic-ref HEAD` と `git status --porcelain` で、想定どおりのブランチ・クリーンな状態であることを確認してください。
2. **通信はすべて通信部経由**: 送信は `MavlinkComm` の `setpoint` / `takeoff` / `command_long` / `set_message_interval`、受信は通信部の受信スレッド 1 本（`mavlink-rx`）だけです。`AR-hook1.py` から `m.mav.*_send` / `mavutil` を直接呼ばず、`AR-hook1.py` に送信ロックを置きません。
3. **`REF_ALT` の高度スケール**: `GLOBAL_POSITION_INT.alt`（AMSL）と同じスケールで設定してください。Motive の GPS 出力（基準点高度 0）を Pixhawk に入れる構成では `0.0` のままで整合します。
4. **起動時のログ確認**:
   - `✓ 目標Yawを ...° に固定（設定ソース: ...）` と `MASK: 0x....`（9c2a5）
   - `ℹ 離陸高度: 1.50m（... 設定ソース: ...）` / `ℹ 離陸の操作: スペースキー（既定 ...）`
   - `✓ 離陸地点のREF座標: ...` / `✓ 離陸高度到達: home相対 1.50m (target Down=...)`（f6152）
   - `✓ MAVLink接続完了` のあと受信スレッドが 1 本だけ動くこと（e22e3）
5. **ATTITUDE 40Hz の帯域**: 25,000µs（`ATTITUDE_MSG_INTERVAL_US`）が通らない環境では 20,000µs（50Hz）へ変更してください。GPS 系（200,000µs）は据え置きです。
6. **yaw を変える場合**: `AR_HOOK_TARGET_YAW_DEG=180.0` のように環境変数で指定します（0〜360、範囲外は起動時に停止）。`MASK` を変える場合は `AR_HOOK_MASK=0x0DF8`。
7. **クランプ上限**: 既定は水平 1.20 m / 上昇 0.30 m / 下降 0.20 m / 最大速度 0.50 m/s です。実機の `LOIT_SPEED_MS` や運用に合わせて `TARGET_MAX_*` を見直してください。CSV の `Target_*` 列で作動状況を確認できます。

9. **手動確認項目（実機）**: Guided + Arm → **スペースキーで離陸**（既定 1.50 m。自動離陸は `AR_HOOK_AUTO_TAKEOFF=1` のときだけ 3 秒後に送信）、キー `u/m/h/l/w/z` の移動、`t` で基準点復帰、検出ロスト時の保持 → 減衰復帰、ATTITUDE 途絶時の目標更新停止（`⚠ MAVLink ATTITUDE が古いため...`）、ケーブル抜けでリンク切断メッセージ + CSV 保存。

## 11. 接続トポロジの決定（GPS_INPUT 15Hz と ArUco 誘導の同時運用 / 2026-11-26）

### 11.4 推奨案と根拠（C 案: AR-hook 自身が `GPS_INPUT` を送る）

**C 案を採用します。**

1. **ポート所有者が 1 つで確定する。** `MavlinkComm` が `/dev/ttyAMA0` を 1 回だけ開き、`GPS_INPUT`（15Hz）も setpoint（最大 40Hz）も同じ `_send_lock` で直列化されます。追加プロセス・追加ポート・追加のサービス依存がありません。
2. **既に実装・試験済みで、このタスクの制約（コード変更なし）と一致する。** `gps_supplier.py` と `MavlinkComm.gps_input()` は `0198b26` で追加され、`test_gps_supplier.py` と SITL 9/9（`gps_input` PASS）で確認済みです。`GPS1_TYPE=14` も `setup_AR-hook1.py` の投入対象に既に含まれます。
3. **遅延・ジッタが最小。** bridge の `serial_lock` を RTCM 断片と共有しないため、誘導 setpoint の周期を GPS 送信が乱しません。
4. **故障影響が既存の運用と一致する。** AR-hook が落ちれば誘導が失われ、実験はその時点で中止です。「GPS だけ残る」B 案の利点は、誘導が無い実験では価値が小さく、USB の新しい故障点の方が大きいと判断します。
5. **A 案は今回の目的に対して過大。** bridge は RTCM 注入用で、複数クライアントのルーティング機能を持ちません。ルータ化は実装・検証コストが大きく、RTCM と誘導を 1 プロセスに集中させます。

**採用条件**: 実機で `GPS_INPUT` が EKF に採用されること（`GPS1_TYPE=14`、位置が Motive と一致、イノベーション過大が出ない）。採用できない場合は B 案を次点として再評価します（USB は `/dev/serial/by-id/...` 固定、`send_GPS3.py` の接続先引数化が前提）。

## 13. `mavlink-bridge.service` の unit 定義（ExecStart 欠落の原因と導入手順 / 2026-11-26）

実機の `mavlink-bridge.service` が **`bad-setting` / `inactive (dead)`**（`Service has no ExecStart=`）で
起動できず、`/dev/ttyAMA0` を service ではなく別端末の手動起動 `python3 send_GPS3.py`
（PID 1084 / ppid 1052 = 対話 bash / pts/0）が占有していた件について、**unit の正典をリポジトリへ追加**しました。

| ファイル | 内容 |
|---|---|

### 13.1 ExecStart 欠落の原因（要点）

| 層 | 内容 |
|---|---|
| 根本原因 | **unit の正典がリポジトリに無かった**（`git log --all -- '*service'` / `-S'ExecStart'` がいずれも 0 件。起動は `RTK/run_rover_bridge.sh` の手動実行だけ）。実機の unit は Pi 上で手作りされ、レビュー・構文チェックの対象外だった |
| 直接原因 | unit 側に **`ExecStart` が存在しない**状態（`[Service]` はあるが `ExecStart` 行が無い／空、`[Unit]` 側に書いている、drop-in に置いていた、のいずれか）。systemd は起動時に `Service has no ExecStart=...Refusing.` で拒否し `inactive (dead)` になる |
| 潜伏した理由 | `systemctl enable` は `[Install]` の `WantedBy=` だけで symlink を作り、**`ExecStart` の有無を検証しない**。壊れた unit が enabled のまま残り、再起動で初めて表面化した（その間に手動の `send_GPS3.py` がポートを取った） |

どの状態かを確定する手順（`systemctl cat` / `systemctl show -p FragmentPath -p DropInPaths` /
`systemd-analyze verify`）は [`systemd/README.md` §3.3](./systemd/README.md) にあります。
**実機の unit ファイルはこの環境から読めないため、確定は人間が実機で実施**してください
（このタスクでは `systemctl start/enable/stop` を実行していません）。

### 13.3 使わない場合（6f183 / C 案 = 現行運用）: mask する

§11.4 のとおり AR-hook 実験では bridge を使わないため、実機では **mask** します。
`mask` は `/etc/systemd/system/<unit>` に symlink を作るので、実ファイルがある場合は先に退避が必要です。

```bash
systemctl cat mavlink-bridge | sudo tee /root/mavlink-bridge.cat.txt      # 調査結果の保全
sudo rm -f /etc/systemd/system/multi-user.target.wants/mavlink-bridge.service
sudo mv /etc/systemd/system/mavlink-bridge.service \
        "/root/mavlink-bridge.service.broken.$(date +%Y%m%d_%H%M%S)"
sudo systemctl daemon-reload
sudo systemctl mask mavlink-bridge
systemctl is-enabled mavlink-bridge     # -> masked
systemctl is-active mavlink-bridge      # -> inactive
```

- mask 後は `systemctl start mavlink-bridge` が `Unit ... is masked.` で失敗します（C 案ではこれが正しい）。
  戻すときは `sudo systemctl unmask mavlink-bridge` → §13.2。
- 詳細（`bad-setting` で `disable`/`mask` が拒否された場合の代替、復帰手順）は
  [`systemd/README.md` §5](./systemd/README.md)。
